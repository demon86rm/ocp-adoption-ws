Multi-cluster GitOps with the Argo CD Agent

This step turns the hub’s Argo CD into the Principal: the component that spokes connect to. It also creates the certificates the Principal needs.

Prerequisites

  • Setup finished: contexts hub, spoke-a, spoke-b work and OpenShift GitOps is installed on all three.

  • argocd-agentctl on your workstation.

The certificates in this step come from argocd-agentctl pki, which Red Hat marks as intended for development and testing only. It is the shortest path for a lab. For production, replace them with certificates issued and renewed by cert-manager (module on production certificates, to be added).

How It Works

  1. The hub ArgoCD gets spec.argoCDAgent.principal. The hub application controller is switched off, because each spoke runs its own controller.

  2. The Principal uses destination-based mapping: an Application or ApplicationSet lives in the hub’s openshift-gitops namespace and picks its spoke with spec.destination.name. The default is one hub namespace per agent. This workshop does not use it, because the ApplicationSet controller ignores the namespace in its template and always creates the generated applications next to itself, where a namespace-mapped agent never sees them. This was found by testing on ROSA HCP.

  3. The Principal takes the agent name from the client certificate common name (auth: "mtls:CN=([^,]+)").

Steps to Apply

1. Enable the Principal

timing not measured yet

What: Merge the Principal settings into the hub’s ArgoCD.

Why: The Principal stays 0/1 and no spoke can connect until it is enabled and has its secrets.

Take a backup first, then patch. A merge patch keeps the other operator settings.

oc get argocd openshift-gitops -n openshift-gitops --context hub -o yaml > hub-argocd.backup.yaml
oc patch argocd openshift-gitops -n openshift-gitops --context hub \
  --type merge --patch-file 01-hub-principal/argocd-principal-patch.yaml

insecureGenerate: false means you supply the certificates in section 2. destinationBasedMapping: true must be set on every agent as well (step 2). Setting it to true makes the Principal generate throwaway ones that agents must not verify. Do not use that outside a lab.

Verify: Principal objects exist 
oc get pod,svc,route -n openshift-gitops --context hub
NAME                                                    READY   STATUS    RESTARTS
pod/openshift-gitops-agent-principal-...                0/1     CrashLoopBackOff   1
pod/openshift-gitops-redis-...                          1/1     Running   0
pod/openshift-gitops-repo-server-...                    1/1     Running   0
pod/openshift-gitops-server-...                         1/1     Running   0

service/openshift-gitops-agent-principal                ...   443/TCP
service/openshift-gitops-agent-principal-resource-proxy ...   9090/TCP

route.route.openshift.io/openshift-gitops-agent-principal   ...

The Principal pod crash-loops (CrashLoopBackOff) until the secrets of section 2 exist. That is expected here. It recovers on its own once they exist (seen on ROSA HCP, GitOps 1.22.4).

Record the route host. Agents dial it and the certificate must name it.

export PRINCIPAL_DNS="$(oc get route openshift-gitops-agent-principal \
  -n openshift-gitops --context hub -o jsonpath='{.spec.host}')"
echo "${PRINCIPAL_DNS}"
To use a load balancer instead of the route, set spec.argoCDAgent.principal.server.service.type: LoadBalancer and server.route.enabled: false, then use the service’s .status.loadBalancer.ingress[0].hostname as PRINCIPAL_DNS.

2. Create the lab certificates and the JWT key

timing not measured yet

What: A self-signed CA, a server certificate for the Principal, a server certificate for the resource proxy, and a signing key for agent tokens.

Why: All Principal and agent traffic is mutually authenticated TLS, and agents receive short-lived tokens signed with the key.

argocd-agentctl pki init \
  --principal-namespace openshift-gitops --principal-context hub

argocd-agentctl pki issue principal \
  --principal-namespace openshift-gitops --principal-context hub \
  --dns "${PRINCIPAL_DNS}"

argocd-agentctl pki issue resource-proxy \
  --principal-namespace openshift-gitops --principal-context hub \
  --dns openshift-gitops-agent-principal-resource-proxy

argocd-agentctl jwt create-key \
  --principal-namespace openshift-gitops --principal-context hub

The --dns value for the Principal must equal the route host. A mismatch shows up as a certificate error in the agent log. Add --ip if agents reach the Principal by IP.

Verify: four secrets exist and the Principal is running 
oc get secrets -n openshift-gitops --context hub | grep agent
oc get pod -n openshift-gitops --context hub | grep principal
oc logs deployment/openshift-gitops-agent-principal -n openshift-gitops --context hub --tail 20
argocd-agent-ca                   kubernetes.io/tls
argocd-agent-jwt                  Opaque
argocd-agent-principal-tls        kubernetes.io/tls
argocd-agent-resource-proxy-tls   kubernetes.io/tls

openshift-gitops-agent-principal-...   1/1   Running   0

... Redis proxy started
... Resource proxy started
... Namespace informer synced and ready

If the pod stays 0/1, restart it: oc rollout restart deployment/openshift-gitops-agent-principal -n openshift-gitops --context hub.

Alternatives Considered

Approach Notes

argocd-agentctl pki (this step)

Fewest commands. Development and testing only

cert-manager

Issues and renews certificates. Needs the operator. Covered in the production module

Organisation PKI

Best for production when a dedicated intermediate CA is available

Reset

Disable the Principal and turn the controller back on first, then delete the secrets.

oc patch argocd openshift-gitops -n openshift-gitops --context hub --type merge \
  -p '{"spec":{"controller":{"enabled":true},"argoCDAgent":{"principal":{"enabled":false}}}}'
oc delete secret argocd-agent-jwt argocd-agent-resource-proxy-tls \
  argocd-agent-principal-tls argocd-agent-ca \
  -n openshift-gitops --context hub --ignore-not-found

The order matters: the Principal reads the secrets, so it must be off before they disappear. The patch also leaves destinationBasedMapping set. Restore hub-argocd.backup.yaml if you want the original object back.
