Multi-cluster GitOps with the Argo CD Agent

Applications need passwords and tokens, and Git is the wrong place for them. This step installs the External Secrets Operator on each spoke. Git then holds only a reference ("get token from the store"), and each cluster resolves it from its own secret store. It also lists what a new spoke needs before it can take part, because this step found a permission gap that every spoke has.

Prerequisites

  • Step 6 finished.

  • The sample repository contains platform/secret-store (a ClusterSecretStore and its reader) and apps/secret-demo (an ExternalSecret and a pod that uses it).

How It Works

  1. The External Secrets Operator for Red Hat OpenShift runs on each spoke. Secrets are resolved on the spoke, so the hub never holds them.

  2. A ClusterSecretStore named workshop-store tells the operator where secrets come from. Here it reads a namespace on the same cluster, so the workshop needs no cloud account. In a real fleet you swap the provider for AWS Secrets Manager, Vault or another store. Applications keep the same ExternalSecret.

  3. An ExternalSecret in the application asks the store for a value and creates a normal Secret from it.

  4. The store and the permissions it needs are the same on every spoke, so a platform ApplicationSet delivers them.

The operator is openshift-external-secrets-operator, channel stable-v1, from redhat-operators. It supports the AllNamespaces install mode only.

Steps to Apply

1. Install the operator and its controller on each spoke

~2 minutes for the operator, ~1 minute more for the controller (measured once on ROSA HCP)

What: Apply the operator subscription, then an ExternalSecretsConfig named cluster.

Why: The operator alone does nothing. The ExternalSecretsConfig asks it to deploy the controller.

spoke-a shares the hub cluster, so the install happens once there.

oc apply -f 07-secrets-bootstrap/external-secrets-operator.yaml --context spoke-a
oc apply -f 07-secrets-bootstrap/external-secrets-operator.yaml --context spoke-b
oc wait csv/openshift-external-secrets-operator.v1.3.0 -n external-secrets-operator \
  --for=jsonpath='{.status.phase}'=Succeeded --timeout=300s --context spoke-a
oc wait csv/openshift-external-secrets-operator.v1.3.0 -n external-secrets-operator \
  --for=jsonpath='{.status.phase}'=Succeeded --timeout=300s --context spoke-b
oc apply -f 07-secrets-bootstrap/external-secrets-config.yaml --context spoke-a
oc apply -f 07-secrets-bootstrap/external-secrets-config.yaml --context spoke-b
Verify: the controller pods run 
oc get pods -n external-secrets --context spoke-a
oc get pods -n external-secrets --context spoke-b
external-secrets-...                  1/1   Running
external-secrets-cert-controller-...  1/1   Running
external-secrets-webhook-...          1/1   Running

Allow a minute. On the first cluster one pod was still 0/1 after 60 seconds and became ready shortly after.

2. Let each spoke’s Argo CD manage External Secrets objects

What: A ClusterRole for the external-secrets.io group, bound to the spoke Argo CD application controller.

Why: Without it the sync fails with clustersecretstores.external-secrets.io is forbidden. A cluster-scoped Argo CD instance only knows the API groups it ships with. A kind added later by an operator needs an explicit grant. Expect the same for any other operator you add.

The file holds the placeholders ARGOCD_NS and ARGOCD_NAME, so apply it through envsubst. spoke-a uses its own instance gitops-spoke-a, and spoke-b uses openshift-gitops.

ARGOCD_NS=gitops-spoke-a ARGOCD_NAME=gitops-spoke-a \
  envsubst < 07-secrets-bootstrap/argocd-eso-rbac.yaml | oc apply --context spoke-a -f -
ARGOCD_NS=openshift-gitops ARGOCD_NAME=openshift-gitops \
  envsubst < 07-secrets-bootstrap/argocd-eso-rbac.yaml | oc apply --context spoke-b -f -
Verify: the bindings exist 
oc get clusterrolebinding --context spoke-a | grep argocd-external-secrets
oc get clusterrolebinding --context spoke-b | grep argocd-external-secrets
argocd-external-secrets-gitops-spoke-a      ClusterRole/argocd-external-secrets
argocd-external-secrets-openshift-gitops    ClusterRole/argocd-external-secrets

3. Deliver the secret store to every cluster

~1 minute

What: An ApplicationSet that deploys platform/secret-store to every tagged cluster.

Why: The store is identical everywhere, so Git and the tag deliver it. It uses the default project because it creates cluster-scoped objects. In a real fleet, give platform components their own project.

oc apply -f 07-secrets-bootstrap/applicationset-platform-secrets.yaml --context hub
Verify: the store is valid on both clusters 
oc get clustersecretstore --context spoke-a
oc get clustersecretstore --context spoke-b
NAME             AGE   STATUS   CAPABILITIES   READY
workshop-store   26s   Valid    ReadWrite      True

4. Create the source secret outside Git

What: On each cluster, create the secret the store reads. Use a different value per environment.

Why: This stands in for your secret manager. Nobody commits it, and test and prod hold different values.

oc create secret generic hello-api-key --from-literal=token=<test-value> \
  -n workshop-secrets-source --context spoke-a
oc create secret generic hello-api-key --from-literal=token=<prod-value> \
  -n workshop-secrets-source --context spoke-b
Use dummy values for the workshop. In a real fleet the value lives in your secret manager, never on a command line.

5. Deploy an application that uses it

~10 seconds

What: An ApplicationSet for apps/secret-demo. Its ExternalSecret asks the store for the token. The pod prints the length of the token, never the value.

Why: This proves the whole path: Git holds a reference, the spoke resolves it.

oc apply -f 07-secrets-bootstrap/applicationset-secret-demo.yaml --context hub
Verify: the secret was created on each cluster from its own source 
oc get externalsecret -n fleet-secrets --context spoke-a
oc logs deploy/secret-demo -n fleet-secrets --context spoke-a --tail 1
oc logs deploy/secret-demo -n fleet-secrets --context spoke-b --tail 1
NAME            STORE            REFRESH INTERVAL   STATUS
hello-api-key   workshop-store   1m                 SecretSynced

token length: <length of your test value>
token length: <length of your prod value>

The two lengths differ, because each cluster resolved its own secret.

Alternatives Considered

Approach Notes

External Secrets Operator (this step)

Resolves on the spoke from a store you already run

Secrets Store CSI driver

Encrypted secrets in Git

Works without a store. The decryption key still has to reach each cluster

Reset

oc delete -f 07-secrets-bootstrap/applicationset-secret-demo.yaml --context hub --ignore-not-found --wait
oc delete -f 07-secrets-bootstrap/applicationset-platform-secrets.yaml --context hub --ignore-not-found --wait
oc delete namespace fleet-secrets workshop-secrets-source --context spoke-a --ignore-not-found
oc delete namespace fleet-secrets workshop-secrets-source --context spoke-b --ignore-not-found
oc delete clusterrolebinding argocd-external-secrets-gitops-spoke-a --context spoke-a --ignore-not-found
oc delete clusterrolebinding argocd-external-secrets-openshift-gitops --context spoke-b --ignore-not-found
oc delete clusterrole argocd-external-secrets --context spoke-a --ignore-not-found
oc delete clusterrole argocd-external-secrets --context spoke-b --ignore-not-found
oc delete clusterrole eso-reader-selfsubjectrulesreviews --context spoke-a --ignore-not-found
oc delete clusterrole eso-reader-selfsubjectrulesreviews --context spoke-b --ignore-not-found
oc delete clusterrolebinding eso-reader-selfsubjectrulesreviews --context spoke-a --ignore-not-found
oc delete clusterrolebinding eso-reader-selfsubjectrulesreviews --context spoke-b --ignore-not-found
oc delete -f 07-secrets-bootstrap/external-secrets-config.yaml --context spoke-a --ignore-not-found
oc delete -f 07-secrets-bootstrap/external-secrets-config.yaml --context spoke-b --ignore-not-found
oc delete -f 07-secrets-bootstrap/external-secrets-operator.yaml --context spoke-a --ignore-not-found
oc delete -f 07-secrets-bootstrap/external-secrets-operator.yaml --context spoke-b --ignore-not-found

The order matters: remove the applications first so nothing recreates the objects, then the cluster-wide roles, then the controller, then the operator. Deleting the Subscription leaves its ClusterServiceVersion behind, so delete the CSV in external-secrets-operator too if you want the operator gone.
