Multi-cluster GitOps with the Argo CD Agent

This page prepares one hub and two spokes. Nothing is created that the later steps depend on except the operator and the named contexts.

Prerequisites

  • Three OpenShift 4.x clusters: one hub and two spokes. Each spoke must reach the hub’s Principal route over HTTPS, and DNS for the hub route host must resolve from the spokes.

  • A user that can install operators on each cluster. This workshop was designed for cluster-admin. See the ROSA note below if you use dedicated-admin.

  • oc, jq, openssl, envsubst, and argocd-agentctl on your workstation. Download argocd-agentctl from the releases of the upstream argoproj-labs/argocd-agent GitHub project, as the Red Hat OpenShift GitOps page Argo CD Agent installation points to. The workshop was drafted with release 0.11.0 (reports Argo CD 3.6.1). If a flag differs on your version, try another release and tell the maintainer.

  • A Git repository you can push to, for the later fleet steps.

ROSA HCP is the intended test platform but is not validated yet. Check three things first. Your login may be dedicated-admin. Managed-service rules may block edits to the default ArgoCD in openshift-gitops. The hub route must be reachable from both spokes. If the second one fails, create your own ArgoCD in a new namespace and use that namespace wherever this workshop says openshift-gitops.
Context Role Notes

hub

Hub

Runs the Principal, the UI and the repo-server. No application controller

spoke-a

Spoke

The same cluster as the hub, to save a cluster. A second Argo CD instance in gitops-spoke-a plays the spoke. Tagged env=test in step 2

spoke-b

Spoke

A separate cluster. Argo CD in openshift-gitops. Tagged env=prod in step 2
Sharing the cluster saves provisioning but is less realistic. spoke-a reaches the Principal through the same router as everyone else, so the remote network path is not tested for it, and anything that breaks the hub cluster breaks spoke-a too. spoke-b is the real test of a remote spoke.

Option A: log in and name the contexts

What: Log in to the three clusters and give each context a fixed name.

Why: Every command in the workshop passes --context, so a wrong default can never touch the wrong cluster.

Put the logins in a personal myenv.sh. The repository ignores it, because it holds passwords.

# myenv.sh - personal, never committed
export HUB_API_URL="https://api.<hub-domain>:6443"
export SPOKE_B_API_URL="https://api.<spoke-b-domain>:6443"
export GIT_REPO_URL="https://github.com/<org>/<fleet-repo>.git"

oc config delete-context hub 2>/dev/null
oc config delete-context spoke-a 2>/dev/null
oc config delete-context spoke-b 2>/dev/null

oc login "$HUB_API_URL" --username <user> --password <password>
oc config rename-context "$(oc config current-context)" hub
# spoke-a is the hub cluster again, under a second context name
oc config set-context spoke-a \
  --cluster "$(oc config view --minify --context hub -o jsonpath='{.contexts[0].context.cluster}')" \
  --user "$(oc config view --minify --context hub -o jsonpath='{.contexts[0].context.user}')"

oc login "$SPOKE_B_API_URL" --username <user> --password <password>
oc config rename-context "$(oc config current-context)" spoke-b
source myenv.sh
Verify: three contexts exist and answer 
oc whoami --context hub
oc whoami --context spoke-a
oc whoami --context spoke-b
oc whoami --show-server --context hub
oc whoami --show-server --context spoke-a
<your user>
<your user>
<your user>
<hub API URL>
<hub API URL>

The last two lines must be identical: spoke-a is the hub cluster.

Option B: contexts already configured

If someone gave you a kubeconfig, name the contexts hub and spoke-b with oc config rename-context <old> <new>. Create spoke-a as a second context for the hub cluster with the oc config set-context spoke-a …​ command above.

Install the GitOps operator on the two clusters

What: Apply one manifest to each cluster. It creates the operator namespace, an OperatorGroup and a Subscription.

Why: The hub needs Argo CD for the Principal. Each spoke needs its own Argo CD, because in this model the spoke runs the application controller. spoke-a shares the hub cluster, so the operator is installed once there.

The channel is set to latest. Pin it to your tested channel when you have one.

oc apply -f 00-setup/gitops-operator.yaml --context hub
oc apply -f 00-setup/gitops-operator.yaml --context spoke-b
Verify: the operator is Succeeded and a default Argo CD exists on each cluster 
oc get csv -n openshift-gitops-operator --context hub
oc get argocd -n openshift-gitops --context hub
NAME                                  DISPLAY                       VERSION   PHASE
openshift-gitops-operator.v1.22.x     Red Hat OpenShift GitOps      1.22.x    Succeeded

NAME               AGE
openshift-gitops   2m

Repeat both commands with --context spoke-b.

Check the cluster scope

What: Confirm the default instance may manage cluster-scoped resources.

Why: The Argo CD Agent requires a cluster-scoped Argo CD instance. On OpenShift GitOps an instance is cluster-scoped when its namespace is listed in the operator’s ARGOCD_CLUSTER_CONFIG_NAMESPACES variable. The default instance in openshift-gitops is already listed. The second instance for spoke-a is not, so the next section adds it.

oc get deployment -n openshift-gitops-operator --context hub -o yaml \
  | grep -A1 ARGOCD_CLUSTER_CONFIG_NAMESPACES
Verify: the variable includes openshift-gitops 
          - name: ARGOCD_CLUSTER_CONFIG_NAMESPACES
            value: openshift-gitops

The value is set by the operator itself, so the Subscription has no config entry for it. If the variable is missing, follow cluster-scoped Argo CD instance in the Red Hat page.

Create the spoke-a instance on the hub cluster

What: Add gitops-spoke-a to the cluster-scoped list, then create a second Argo CD in that namespace.

Why: The agent needs its own application controller, and the hub’s Argo CD has its controller turned off in step 1. It must be cluster-scoped, so its namespace joins the operator’s list.

The patch below replaces the whole env list of the Subscription. Read the current value first (previous check) and keep every entry. If your value is not just openshift-gitops, put it before the comma. On ROSA HCP the Subscription may be locked. That is not validated. 
oc patch subscription openshift-gitops-operator -n openshift-gitops-operator --context hub \
  --type merge -p '{"spec":{"config":{"env":[{"name":"ARGOCD_CLUSTER_CONFIG_NAMESPACES","value":"openshift-gitops,gitops-spoke-a"}]}}}'
oc apply -f 00-setup/argocd-spoke-a.yaml --context hub
Verify: the instance is running and the operator restarted with the new value 
oc get argocd -n gitops-spoke-a --context spoke-a
oc get pods -n gitops-spoke-a --context spoke-a
NAME             AGE
gitops-spoke-a   1m

gitops-spoke-a-application-controller-0   1/1   Running
gitops-spoke-a-redis-...                  1/1   Running
gitops-spoke-a-repo-server-...            1/1   Running

Clone the repository

git clone https://github.com/<org>/ocp-adoption-ws.git
cd ocp-adoption-ws/ocp-gitops-agent-ws

Reset

The setup creates only the operator. Remove it in reverse order of creation.

oc delete -f 00-setup/argocd-spoke-a.yaml --context hub --ignore-not-found
oc delete -f 00-setup/gitops-operator.yaml --context spoke-b --ignore-not-found
oc delete -f 00-setup/gitops-operator.yaml --context hub --ignore-not-found
The Subscription patch is not undone by the commands above. Set ARGOCD_CLUSTER_CONFIG_NAMESPACES back to openshift-gitops if you want the original value. Deleting the Subscription leaves the installed ClusterServiceVersion and the openshift-gitops namespace in place. Delete the CSV with oc delete csv -n openshift-gitops-operator --all --context <ctx> if you want the operator gone.
